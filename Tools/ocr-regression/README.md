# ScreenshotPlaceScanner 회귀 검사

```
python3 Tools/ocr-regression/check.py
```

의존성 없음. 실패하면 종료 코드 1.

## 왜 있나

`ScreenshotPlaceScanner`는 정규식과 레이아웃 규칙 더미다. 그런 코드는
한쪽을 고치면 다른 쪽이 조용히 깨진다. 이 검사를 만드는 동안 실제로 두 번
겪었다.

- 주소 패턴에 `읍/면`을 허용했더니 **`평양냉면`의 "면"이 행정구역으로
  잡혀** 음식 종류가 주소에 섞였다.
- 행정구역 조각(`안양시 동안구`)을 이름에서 걸러내는 규칙을 넣었더니
  **`함흥곰보냉면`·`마부시`·`양수면옥`이 같이 죽었다.**

둘 다 다른 세트가 잡아 줘서 알았다.

## 무엇이 아닌가

**이 검사는 OCR 정확도를 재지 않는다.** Vision(`VNRecognizeTextRequest`)은
여기서 실행할 수 없다. 픽스처는 **인식이 끝난 뒤의 텍스트와 좌표**에서
시작하며, 따라서 검사 대상은 그 뒤의 추출 규칙뿐이다.

인식 자체의 정확도와 기기 동작은 실제 기기에서 확인해야 한다.

## `_scanner_port.py`는 거울이다

Swift 원본의 파이썬 포팅본이다. 스스로 진실이 아니다.
`ScreenshotPlaceScanner.swift`의 규칙이나 상수를 고치면 **여기도 같이
고쳐야 한다.** 안 그러면 존재하지 않는 코드를 검사하게 된다.

CI(`.github/workflows/ci.yml`)는 빌드만 돌리고 이 검사는 돌리지 않는다 —
이 저장소에는 테스트 타깃이 없다. 스캐너를 건드렸으면 직접 실행할 것.

## 픽스처 네 세트

| 세트 | 출처 | 보는 것 |
|---|---|---|
| **인스타 게시물** (15곳) | 실제 캡처 8장을 옮겨 적음 | 이름과 주소가 **한 줄에** 있는 경우. 이전 구현이 가장 크게 실패하던 형태 |
| **홀드아웃** (9건) | 합성 | 일반화와 오탐. 주소 없는 목록에서 **아무것도 내놓지 않는지**, 도로명이 든 설명문에 속지 않는지 |
| **인천 목록** (8곳) | 실제 캡처, 좌표 실측 | 세로 목록형. 카테고리 배지가 이름과 같은 행 오른쪽에 있어, **좌표 없이는 배지를 이름으로 오인**한다 |
| **블루리본 표** (18곳) | 실제 캡처, 열 좌표 실측 | 3열 표. **중간 열(음식종류)을 이름으로 잘못 고르지 않는지** |

좌표가 실측인 두 세트는 **좌표만 실측이고 텍스트는 보정**이다. 좌표는 실제
스크린샷에 tesseract(kor)를 돌려 얻었지만 그 인식 품질이 Vision과 다르고
상호 여럿을 뭉갰다 — 그대로 두면 인식률 문제가 규칙 문제를 가린다.

## 알려진 한계

`홀드아웃 / 지도앱 장소화면`의 기대값은 **옳은 답이 아니라 현재 동작**이다.
지도 앱은 제목과 주소 사이에 카테고리 줄을 넣고(`스타벅스 강남대로점` /
`카페` / `서울 강남구 강남대로 390`), 위쪽 역추적이 `카페`를 먼저 집는다.

가장 *큰* 후보를 고르게 바꾸면 이 건은 풀리지만 인천 목록이 깨진다 — 섹션
제목(`인천`)이 어느 항목보다 크게 그려져 있다. 양쪽을 재 보고 "가장 가까운
쪽"을 택했다. 그 행도 주소는 올바로 들고 가므로, Google 검증이 확정을
거부하고 사용자에게 남긴다(틀린 카드가 저장되지는 않는다).

이 기대값이 깨지면 누군가 그 한계를 고쳤다는 뜻이다. 픽스처를 갱신하면 된다.
